# 漫步者 Fit900NB Turbo 协议笔记

本文记录本项目用到的协议细节。**2026-11-08 拿到了真机 HCI 抓包（固件 1.0.3）**，所以 Fit900NB Turbo 的部分不再是推测——每一条都标了来源。

抓包文件：`BT_HCI_2026_1108_142340.cfa.curf`（安卓 HCI snoop，btsnoop 格式），操作发生在 14:29:30–14:33:57 之间（实际解析到的帧从 14:29:35 到 14:33:08），来自官方 App 的一次完整操作（降噪三档 → 环境声三档 → 关闭 → 场景三段 → 音效六档 → LDAC 三档）。

## 1. 传输层

耳机通过 BLE GATT 暴露一个厂商私有服务：

| 项目 | UUID | 方向 |
| --- | --- | --- |
| 服务 | `4809xxxx-1a48-11e9-ab14-d663bd873d93` | — |
| 写 | `48090002-1a48-11e9-ab14-d663bd873d93` | App → 耳机 |
| 通知 | `48090001-1a48-11e9-ab14-d663bd873d93` | 耳机 → App |

- 实现里按前缀 `4809` + 后缀 `-1a48-11e9-ab14-d663bd873d93` 匹配，并保留「任意同时可写 + 可通知的服务」作为兜底。
- 单次写入长度 = MTU − 3；应用连接后尝试 `requestMtu(247)`，Windows 通常不支持，回落到 20 字节分片。
- 回包可能被拆段，也可能两帧粘在一起，解码器必须是增量的。

## 2. 帧格式：BES v2 明文（已确认）

```
AA | EC | cmd | lenHi | lenLo | payload... | sum8
```

- `sum8 = Σ 前面所有字节 & 0xFF`
- **Fit900NB Turbo 用明文，不做 0xA5 异或**（这一点很容易搞错：异或只影响 payload，所以早期只能靠「读名称看回包是否可读」来区分）
- 回包首字节是 `BB`，结构一致

实测一条：

```
写入  AA EC C1 00 02 2F 02 8A
回包  BB EC C1 00 02 2F 02 96
```

## 3. 命令表（全部真机确认）

| 命令 | 含义 | 回包 |
| --- | --- | --- |
| `0xD0` | 电量 | 1 字节百分比（抓包里是 `2D` = 45%） |
| `0xC6` | 固件版本 | 3 字节 `主.次.修订`（`01 00 03` = 1.0.3） |
| `0xC9` / `0xCA` | 读 / 写名称 | UTF-8，`EDIFIER Fit900NB Turbo` |
| `0xD8` | 型号指纹 | 25 字节，全型号固定 |
| `0xCC` / `0xC1` | 读 / 写降噪 | `[2F, ...]`，见下 |
| `0x08` / `0x09` | 读 / 写场景 | 读回 `[场景, 0x06]` |
| `0xD5` / `0xC4` | 读 / 写音效 | 单字节预设号；非音乐场景读回 `0xFF` |
| `0x91` / `0x92` | 通用设置读 / 写 | `[项 id, 值]`；LDAC = 项 `0x11` |
| `0xC3` | 未知 | 固定回 `03` |
| `0x68` | 未知（连接状态？） | 回 `0C` 或 `00` |
| `0x05` | 提示音音量 | 回 `00` |
| `0xFB` | 心跳 / 保活 | 无回包 |
| `0xF0` | 按键循环设置 | `F0 0A` → `[0A 02 19]`；`F0 05` → `[05 03]` |
| `0xFD` | 未知 | `[03 01]` |

## 4. 降噪：槽位 0x2F

`0xCC` 读（**空 payload**）→ `[2F, 模式]`；`0xC1` 写 `[2F, 模式]`，切环境声时写 `[2F, 04, 等级]`。

| 模式值 | 含义 | 写入 |
| --- | --- | --- |
| 1 | 深度降噪 | `C1 [2F 01]` |
| 2 | 舒适 | `C1 [2F 02]` |
| 3 | 防风噪 | `C1 [2F 03]` |
| 4 | 环境声 | `C1 [2F 04 等级]` |
| 5 | 关闭 | `C1 [2F 05]` |

环境声等级（第三个字节）：

| 值 | 含义 |
| --- | --- |
| 1 | 突出人声 |
| 2 | 平衡 |
| 3 | 突出背景声 |

读等级的坑：`0xCC` **永远只回 2 字节**，即使当前是环境声也不带等级。官方 App 的做法是发
`0xC1 [2F 04]`（不带第三字节），耳机回 `[2F 04 等级]`，把记住的等级带回来——抓包 14:30:30
就是这条（去程 `2F 04`，回程 `2F 04 02`）。本项目在探测到「当前处于环境声」后补发一次这条命令
来填 UI 的档位；模式不变，没有副作用。

**没有 `0x1B` / `0x10` / `0x17` 那些槽位**——这是之前按同代型号推断错了的地方。

官方宣传的五档「深度 / 舒适 / 防风 / 环境声 / 关」正好对应 1–5。

## 5. 场景（不是「游戏模式」）

`0x09` 写 `[值]`，`0x08` 读 → `[场景, 0x06]`。

| 值 | 含义 |
| --- | --- |
| 0 | 音乐 |
| 1 | 游戏（低延迟） |
| 2 | 空间音效 |

**重要联动**：只要场景不是「音乐」，`0xD5` 就读回 `0xFF`，此时 `0xC4` 写音效无效——音效预设被场景接管了。UI 里必须把音效控件置灰，否则用户会以为坏了。

## 6. 音效预设

`0xC4` 写 `[预设号]`（回 `[01]` 表示接受），`0xD5` 读 `[预设号]`。

| 值 | 名称 |
| --- | --- |
| 0 | 纯正 |
| 1 | 动感 |
| 2 | 人声 |
| 3 | 低音增强 |
| 4 | 高音增强 |
| 5 | 发烧友 |

顺序**不是**按数值排的，官方 App 的排列是：人声 → 低音增强 → 动感 → 纯正 → 高音增强 → 发烧友。本项目按这个顺序显示。

## 7. LDAC

走通用设置通道：`0x92` 写 `[0x11, 档位]`，`0x91` 读 → `[0x11, 档位]`。

| 值 | 含义 |
| --- | --- |
| 0 | 关闭 |
| 1 | 44.1 / 48 kHz |
| 2 | 96 kHz |

写回包是 `[0C, 档位]`（注意不是回显 `11`）。

切换 LDAC 会让耳机重连，链路会短暂断开；应用会在重连后重新读取状态。

## 8. 连接时的读取流程

```
1. 0xD0 读电量（连接后的第一条命令偶尔会被丢掉，没回包就问第二次）。
2. 0xC9 读名称、0xC7 读固件、0xD8 读指纹。
   （0xC8 读 MAC 在这台耳机上从没出现过，应用不发这条。）
3. 读控制项：降噪 0xCC、环境声等级 0xC1 [2F 04]（仅当前是环境声时）、
   场景 0x08、音效 0xD5、LDAC 0x91。
```

0.8.8 起不再有「协商」这层概念：

- 帧格式固定是 **BES v2 明文**，不会再去试 v1 或异或版本；
- 降噪固定用槽位 `0x2F`，不会试探 `0x1B` / `0x10` / `0x17`；
- 没有型号档案，也不识别设备名 —— 连上什么设备都按 Fit900NB Turbo 发命令。

电量查询失败会被当作「链路没通」，控件保持上一次可用的状态；
降噪查询失败只会让档位显示为「未知」，控件本身不会消失（这只耳机一定有降噪）。

## 9. 仍然未知的部分

1. `0xC3`、`0x68`、`0xFD` 的语义没有确定，代码里不主动发送。
2. `0xF0` 的按键循环掩码只在抓包里看到两次读取，没有做写入验证，UI 未开放。
3. 自定义 EQ（如果有）需要更长的抓包；目前只看到 6 组预设。
4. 双设备连接、固件升级未涉及。
