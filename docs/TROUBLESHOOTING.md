# 扫不到 / 连不上耳机？先看这里

目标设备：**EDIFIER Fit900NB Turbo**。

## 一句话结论

> 这只耳机有**两个地址**。Windows 设备属性里显示的是**经典蓝牙**地址，
> 而 BLE（GATT）用的是另一个地址。拿经典地址去连，WinRT 只会回一句
> `Failed to get device` —— 因为它的 BLE 栈里根本没有那个地址。

| 用途 | 地址 |
| --- | --- |
| 经典蓝牙（A2DP / HFP / AVRCP，听歌打电话） | `6C:16:29:E7:B5:14` |
| **BLE 广告 / GATT（本应用连这个）** | **`6C:16:29:E7:B5:41`** |

两个地址只在最后一字节不同，前缀 `6C:16:29:E7:B5` 相同。

## 这个结论是怎么来的

从真机抓包（`BT_HCI_2026_1108_142340.cfa.curf`）里解出的广播包：

```
广告地址 = 6c:16:29:e7:b5:41
厂商数据 = e0 07 | 6c 16 29 e7 b5 14 | 02 00
           ↑公司ID  ↑经典蓝牙 MAC        ↑状态
```

也就是说：**耳机自己在广播里写明了「我的经典地址是 …:14」，
但它用来广播/被连接的 BLE 地址是 …:41。**

同一份抓包里另外两台漫步者设备也是同样的规律：

| 广告地址 | 厂商数据里的经典 MAC |
| --- | --- |
| `c8:24:78:20:82:59` | `c8:24:78:55:64:ca` |
| `6c:16:29:e7:b5:41` | `6c:16:29:e7:b5:14` |

所以这不是个例，是 BES 方案耳机的通用行为。

## 应用怎么处理（0.7.0）

1. **默认地址就是 BLE 地址** `6c:16:29:e7:b5:41`，装上直接连；
2. **自动学习**：扫描时只要看到厂商数据里带着 `…:14`，就知道那台是这只耳机，
   把它当时的 BLE 地址记下来（换耳机、换批次都能自己纠正）；
3. **填错也不怕**：在「设置 → 我的耳机」里填了经典地址，连接失败后会自动换 BLE 地址再试一次，
   成功后把正确地址存下来；
4. 旧版本存下的经典地址会在启动时**静默迁移**成 BLE 地址。

## 怎么自己看这两个地址

经典地址（Windows 属性）：

```powershell
Get-PnpDevice -FriendlyName '*Fit900*' | Select-Object FriendlyName, InstanceId
# BTHENUM\DEV_6C1629E7B514\...   →  6C:16:29:E7:B5:14
```

BLE 地址（应用扫描页里直接看）：扫描页把来源切到「蓝牙扫描」，
找那一行带「我的」徽标的设备，地址就显示在名字下面。
Windows 的 BLE 绑定若存在，也会出现 `BTHLE\DEV_<BLE地址>` 节点：

```powershell
Get-PnpDevice -Class BluetoothLE | Select-Object FriendlyName, InstanceId
```

## 常见失败对照

| 报错 | 含义 | 处理 |
| --- | --- | --- |
| `Failed to get device` | 这个地址在 Windows 的 BLE 栈里不存在 | 你填的是经典地址；用默认的 BLE 地址，或扫描一次让它自动学 |
| `Failed to get characteristics for service 48097303…: AccessDenied` | 耳机暴露了一个**要求加密链路**的厂商服务，连接枚举到它就被拒 | 见下面「AccessDenied」一节 |
| 连接超时 / `Unreachable` | 耳机被 Windows 当音频设备占着 | 先在系统里断开音频，再回来连 |
| 连上但读不到数据 | GATT 通了但耳机不回包，日志里是「电池查询无应答（本轮共收到 0 帧通知…）」 | 多半是订阅了别的通知口（例如 `0000ff18`）；0.8.4 起按特征值配对并逐个通道试，见下面「连上了但耳机不回包」 |
| 列表里连耳机都没有 | 没在广播 | 让耳机断开系统连接 / 重新进入配对模式，再扫一次 |

## 连上了但耳机不回包（电池查询无应答）

现象：BLE 连接成功，日志里只有 `TX D0`，没有 `RX`，最后一句是
`电池查询无应答（本轮共收到 0 帧通知：一帧都没有，先查通道和订阅）`；电池、降噪、音效全都读不出来。

有两个已知原因，0.8.4 都修了：

### 原因 1：Android 回包里的地址是大写（0.8.2 及以前）

`UniversalBle.onValueChange` 在 Android 上给的是 `BluetoothDevice.address`，
形如 `6C:16:29:E7:B5:41`，而应用里存的是小写 `6c:16:29:e7:b5:41`。
旧代码用 `==` 比较，于是**每一帧回包都被丢掉**：不是耳机不回，是应用没接住。
Windows 侧插件输出的是小写，所以只有 Android 会这样。
现在统一走 `BleController.sameAddress()`，大小写、短横线、空格都兼容。

### 原因 2：订阅错了通知口（0.8.3 及以前）

2026-10-19 的真机日志（Windows）：

```
INFO 通道 service=48097303-1a48-11e9-ab14-d663bd873d93
     write=48090002-1a48-11e9-ab14-d663bd873d93
     notify=0000ff18-0000-1000-8000-00805f9b34fb
TX   TX D0 ← [] (v1, 5B)   ×2
TX   TX D0 ← [] (v2, 6B)   ×2
INFO 电池查询无应答，协商失败（本次共收到 0 帧通知）   ← 0.8.3 时代的文案
```

`48097303-…` 这个服务里其实有三个特征：

| 特征 | 属性 | 用途 |
| --- | --- | --- |
| `48090001` | notify | **厂商回包（真正的通知口）** |
| `48090002` | write | **厂商命令（真正的写口）** |
| `0000ff18-…` | notify | 同服务里另一个可通知的特征，不是厂商通道 |

`48097303` 本身是需要加密链路的服务（所以没配对时会 `AccessDenied`），
配对之后它才可枚举 —— 里面就放着真正的控制口。
Windows 插件用 `unordered_map` 存特征，遍历顺序是哈希序而不是声明序，
旧代码「每个服务取第一个可通知的」就选中了 `0000ff18`。
命令写进了 `48090002`（对的），回包却在 `0000ff18` 上等（错的），
所以一帧都收不到，电量/降噪/音效全部读不出来。

0.8.4 起：

1. 按**特征值**做「写 × 通知」配对，`48090002` + `48090001` 得分最高；
2. 标准 GATT 特征（`0000xxxx-0000-1000-8000-00805f9b34fb`）降权；
3. 一个配对谈不下来就退订、换下一个；
4. 实验室日志第一行会打印实际用的写/通知通道，并把整张 GATT 服务表打出来；
   如果通知特征不是 `48090001`，还会额外警告一句。

## AccessDenied：为什么连上了却读不到服务

```
Failed to get characteristics for service
48097303-1a48-11e9-ab14-d663bd873d93: AccessDenied
```

这不是地址问题，连接已经建立了。问题在于：

1. 这只耳机在 BLE 里除了控制服务（`48090001/48090002`）之外，还暴露了一个
   **受保护的服务** `48097303-…`（多半是 OTA / 工厂测试口），
   它的属性要求**加密链路（bonding）**；
2. universal_ble 的 Windows 实现是**逐个服务**取特征值的：
   ```cpp
   for (GattDeviceService &&service : gatt_services) {
     characteristics_result = co_await service.GetCharacteristicsAsync(Uncached);
     if (失败) { gatt_discovery_error = ...; break; }   // 整个连接判失败
   }
   ```
   只要这一个服务被拒，**整个连接就失败** —— 剩下能用的服务它也拿不到。

### 应用的处理（0.8.0）

- 连接失败且错误含 `AccessDenied` / `Failed to get characteristics` 时，
  先 `UniversalBle.pair()` 让 Windows 做一次 **LE bonding**，再重连一次；
- 设置 →「我的耳机」有「**配对耳机**」按钮，可以手动触发；
- 配对成功一次后 Windows 会记住密钥，之后连就不再被拒。

### 还是不行时

1. 设置 → 蓝牙和设备 → 这台耳机 → **删除设备**；
2. 让耳机进入配对模式，重新配对（这次 Windows 会同时建经典 + LE 绑定）；
3. 回到应用点「连接我的耳机」，或设置里点「配对耳机」后再连。

> 如果你**从来没有**让 Windows 走过 LE 配对，系统里就不会有 `BTHLE\DEV_6c1629e7b541`
> 节点 —— 可以先用下面的命令确认：
> ```powershell
> Get-PnpDevice -Class BluetoothLE | Select-Object FriendlyName, InstanceId
> ```

## 0.8.5：点选项没反应 / 探测后反而失败 / 重进卡 20 秒

这三个现象都跟「协商状态被写坏」和「上一次连接没断干净」有关，0.8.5 的处理：

| 现象 | 原因 | 现在的做法 |
| --- | --- | --- |
| 刚连上时点选项没反应 | 那次读取没拿到回读（丢帧），或通知口刚订阅还没稳定 | 写命令有回包就按已生效处理；失败会自动重读一次再执行 |
| 点一次「重新读取」后恢复正常 | 上一次读取时丢了帧，能力表没补齐 | 连接后会自动读一次；仍缺就点「重新读取」 |
| 再点一次「重新读取」后反而全部失败 | 两次读取并发，状态互相覆盖 | 读取串行化（并发请求复用同一轮）；失败自动回滚到上一次可用状态。0.8.8 起帧格式固定 v2，不存在「误判成异或」这回事 |
| 退出重进直接报 `TimeoutException after 0:00:20` | 退出时先做 Dart 清理、没先把系统连接断干净，Windows 留下了半开连接 | 退出先断链（最多 5 秒）再清理；连接前先清理残留连接；连接失败自动重试 3 次（每次 12 秒） |

如果升级后仍然在「进入应用」时报超时：

1. Windows 设置 → 蓝牙和设备 → 删除这台耳机，重新配对一次；
2. 确认没有别的程序（官方 App、Web Bluetooth 页面）同时占着这条连接；
3. 设置 →「我的耳机」→ 先点「断开」，再点「连接我的耳机」。

## 0.8.9：点 × 之后进程还在 / 重复启动提示「已经在运行」

**症状**：点了窗口右上角的 ×，窗口没了，但任务管理器里 `EdifierFitControl.exe`
还在；耳机也一直连着。再双击图标，要么提示**「程序已经在运行」**，
要么（0.8.8 及更早）显示「已断开」并不停重连。

**原因**：Flutter 的 Windows 引擎会先把 `WM_CLOSE` 交给 Dart 的
`onExitRequested` 回调，只有 Dart 回答 `exit` 才真正结束进程。旧版本在回调里
等「断开耳机」完成，而这一步没有超时 —— 蓝牙插件一旦不回话，进程就永远留在后台，
GATT 连接也不会释放。新实例再去抢同一只耳机，就成了「假断开 + 一直重连」。

**0.8.9 的处理**：

1. × 与设置里的「退出应用」走同一条路径：断开 → 最多 8 秒 → 强制 `exit(0)`；
2. 启动时用文件锁做单实例互斥，重复启动会明确提示，而不是去抢连接；
3. 退出时显示「正在断开耳机并退出…」，最多 8 秒，不会无限等。

**升级后还遇到旧进程？** 旧版本不认这个锁。先在任务管理器里结束一次
`EdifierFitControl.exe`（详情里确认没有窗口），再启动 0.8.9 即可。
之后点 × 就会正常退出。

## 0.8.6：Android CI 里的 Gradle 504

`gh run view` 里如果看到这一行，说明 Gradle 分发包的下载源在抽风，不是代码问题：

```
Exception in thread "main" java.io.IOException: Server returned HTTP response code: 504
for URL: https://github.com/gradle/gradle-distributions/releases/download/v9.3.1/gradle-9.3.1-bin.zip
```

`services.gradle.org` 和 `downloads.gradle.org` 现在都会 307 到 GitHub Releases，
GitHub 的 release 资源一抖，wrapper 就整条链路失败。0.8.6 的 workflow 会：

1. 依次尝试官方源 + 华为云 / 南京大学 / 腾讯云镜像 + `downloads.gradle-dn.com`；
2. 把 `~/.gradle/wrapper/dists` 缓存到 Actions Cache，成功过一次就不再依赖网络；
3. 全部失败时用 runner 自带的 Gradle 兜底；
4. 准备完先跑 `./gradlew --version` 验证，失败会直接给出 `::error::` 注解。

## 已知的平台限制

- universal_ble 3.2.0 的 `getSystemDevices()` 在 Windows 上**只枚举已连接设备**，
  `paired` 字段也没有被 native 侧填充 —— 「只列已配对（含未连接）」在 Dart 层做不到。
  折中：固定 BLE 地址（默认行为）+「系统设备」列表。
- 不改第三方插件的 native 代码，保持依赖为上游原版。
